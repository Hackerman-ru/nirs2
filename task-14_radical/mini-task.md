# Мини-задание по статье "Running Consistent Applications Closer to Users with Radical for Lower Latency"

### Выполнил Корняков Санан Арсланович

## Описание статьи

Статья описывает Radical - фреймворк, позволяющий приложениям, требующим строгой согласованности, работать на границе сети с низкой задержкой. Чтобы преодолеть высокие накладные расходы на координацию с центральным хранилищем, Radical использует сочетание статического анализа кода для предсказания операций чтения/записи и спекулятивного выполнения функций на локальном кэше.

## 1. Calvin: Fast Distributed Transactions for Partitioned Database Systems
*Thomson et al. (SIGMOD ’12)* - Ссылка [61] в списке литературы.

### Основная идея статьи Calvin

Calvin - это система обработки транзакций, которая отказывается от классического протокола двухфазной блокировки в пользу детерминированного упорядочивания. Основная идея заключается в том, что если транзакции выполняются детерминировано, то репликам не нужно координировать каждое действие. Для этого Calvin требует знать набор чтения и записи транзакции до начала её выполнения. Если набор данных известен заранее, система может спланировать выполнение так, чтобы избежать конфликтов и блокировок в процессе работы.

### Развитие идеи в Radical

Авторы Radical заимствуют концепцию предварительного знания read/write set и детерминированного выполнения, но решают проблему их получения иначе:
-   Статический анализ вместо разведки: В Calvin для транзакций со сложной логикой (когда набор ключей зависит от прочитанных данных) используются разведывательные транзакции, что добавляет задержку. Radical же использует статический анализ кода serverless-функций (с помощью инструмента, основанного на Eunomia), чтобы вывести read/write set автоматически до исполнения
-   Применение на Edge: Radical использует знание read/write set не для упорядочивания внутри одной БД, как Calvin, а для создания Lock-Validate-WriteIntent (LVI) запроса. Это позволяет отправить один запрос в центральный дата-центр, который сразу проверит валидность данных и захватит блокировки, пока функция выполняется спекулятивно на краю сети

## 2. Rethink the Sync: Speculative Execution in a Distributed File System
*Nightingale et al. (SOSP ’06 / TOCS ’08)* - Ссылка [21, 47] в списке литературы, также упоминается Zyzzyva [40].

### Основная идея Speculative Execution

Работа "Rethink the Sync" (и похожие на нее, например, Zyzzyva для BFT) предлагает использовать спекулятивное выполнение для скрытия задержек ввода-вывода или сетевого взаимодействия. Вместо того чтобы блокировать работу приложения в ожидании подтверждения записи на диск или ответа от реплик, система позволяет приложению продолжить выполнение, предполагая, что операция завершится успешно. Если предположение оказывается неверным, система откатывает состояние назад. Это позволяет пользователю воспринимать систему как более быструю.

### Развитие идеи в Radical

Radical переносит идею спекулятивного выполнения из контекста "ОС - Диск" или "Клиент - Сервер" в контекст "Edge-локация - Cloud-хранилище":
-   Проблема PRAM: Из-за теоремы, ограничивающей скорость доступа к памяти (PRAM result), невозможно получить одновременно и низкую задержку, и строгую согласованность, если данные далеко. Radical обходит это ограничение не физически, а воспринимаемо пользователем
-   Параллелизм: Radical запускает функцию спекулятивно на локальном (edge) кэше (хотя он может быть несогласованным), одновременно отправляя LVI-запрос в центральное хранилище
-   Новизна протокола: В отличие от классических систем, где спекуляция может требовать сложного отката, Radical в случае ошибки валидации (неверной спекуляции), просто переключается на выполнение функции в центральном дата-центре (fallback) и возвращает результат оттуда. Таким образом, Radical скрывает сетевую задержку (RTT) до центрального хранилища за временем выполнения самой функции
