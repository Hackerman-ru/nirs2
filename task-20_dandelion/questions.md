# Вопросы по статье "Unlocking True Elasticity for the Cloud-Native Era with Dandelion"

### Выполнил Корняков Санан Арсланович

## Описание

Статья описывает Dandelion - облачную платформу, достигающую высокой эластичностью для FaaS задач по сравнению с аналогами за счёт смены интерфейса: не POSIX функции, а декларативный DAG из чистых compute-узлов и communication-узлов. Это позволяет запускать вычисления в сверхлёгких песочницах. В результате снижаются хвосты задержек, при проигрывании Azure Functions trace уменьшается закоммиченная память на 96% и p99‑латентность на 46% относительно Firecracker + Knative, а для коротких serverless SQL‑запросов достигается −40% по латентности и −67% по стоимости по сравнению с AWS Athena.

## Вопросы

1. Python SDK и системные вызовы

    В статье сказано, что CPython собран с C SDK Dandelion, но в изменённом dlibc/dlibc++ используется виртуальная in‑memory ФС и заглушённы системные вызовы, которые перехватываются через ptrace.
    Возникают следующие вопросы:
    - Какие модули стандартной библиотеки Python на практике совместимы и работают в такой среде
    - Как ограничивается использование C‑расширений, потенциально вызывающих syscalls/порождающих потоки
    - Какие средства вы рекомендуете разработчикам для верификации того, что используемые библиотеки не совершают недопустимых системных вызовов (например, статический/динамический анализ, тесты)?

2. Наблюдаемость и логирование без POSIX

    Так как compute‑функции не делают системных вызовов, а всё внешнее IO вынесено в доверенные communication‑движки, предусмотрен ли в Dandelion стандартный канал телеметрии/логов для compute‑кода (например, структурированные события через виртуальную ФС или канал рантайма)? Если да, как обеспечиваются масштабирование и многоарендная изоляция (квоты, backpressure, защита от noisy neighbor, изоляция потоков логов по арендаторам/композициям)?
